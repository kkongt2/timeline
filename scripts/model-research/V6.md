# v6: all candidates plus validated selective candidates

No live odds are collected. The site retains one place horse and one quinella-place
pair for every available race. A separate selection badge is conditional on a
frozen rule passing evaluation; no threshold is invented merely to display badges.

## Data and features

`collect.py --start 20210101 --end 20260910` expands the official daily reports.
The manifest retains source URLs, hashes, download errors and parse exclusions.
`features_v6.validate_rows` additionally rejects duplicate races/starters,
ambiguous finishes, payout-rule mismatches and implausible race conditions.
DNFs and tied finishes remain excluded rather than silently changing field size.
This exclusion can bias the historical sample and is disclosed.

The first year is warm-up. The shared `features_v6.py` builds 32 pre-race features:
shrunk annual and distance records; relative rating and burden; previous-race
distance/burden changes; normalized recent finishes, trend and consistency;
previous time margins normalized to 1,200 metres; a historical clock reference
grouped by venue/distance/past track condition; previous opponents' ratings;
horse/jockey history; field conditions and missing-history indicators.

Clock references are frozen for each date. All history is strictly earlier than
the predicted date. Current race times, finish labels, odds, current body weights
and current track state are never prediction inputs. This is a historical speed
proxy, not an official speed index. Horse identity uses venue plus name, so
renaming and transfers can lose history. History retains a year and at least ten
starts; distance counts describe that retained history, not a lifetime record.

`History.export` and `attach` are used by both the evaluation and live updater.
The browser receives precomputed feature arrays with a version and history cutoff.
Missing arrays, mismatched field size/distance, a same-day/future cutoff, or a
history cutoff older than seven days trigger the existing model fallback.
Refreshing prior completed dates is separate from retraining the frozen model.

## Evaluation protocol

Each bet type independently compares five configurations: logistic regression on
all history; gradient-boosted trees on one year, three years, all history, and all
history with a 365-day half-life. Each race has equal training loss weight; many
pairs from one race are never counted as independent races.

Candidate choice uses three expanding chronological folds: 2024 H2, 2025 H1,
2025 H2. Training in each fold ends before its evaluation begins. The final model
is fit before 2026-01-01. Model choice uses top-candidate hit rate, with Brier as
a tie-breaker. The two prediction targets are actual place-rule qualification
and two horses both finishing in the first three.

- January–February 2026: monotonic logistic probability calibration.
- March–April 2026: choose one selection rule and freeze eligible venues.
- May–15 July 2026: confirm that frozen rule, with minimum sample and coverage
  gates and a date-cluster bootstrap lower bound above zero for selective-minus-all
  hit rate. Venue eligibility is not selected using confirmation outcome labels.
- 16 July–10 September 2026: reused historical audit. This overlaps v5's earlier
  test and is explicitly not a new untouched or prospective test.

The deployment guard compares the audit with the frozen incumbent on the same
valid races. A bet type can switch only if hit rate does not decline and the
paired date-bootstrap lower bound is at least -2 percentage points. This is a
non-degradation guard, not proof of improvement. Statistical improvement is
reported separately only when the lower bound is positive. A failed all-race model stays inactive for the general candidate track.
The separate selective track can serve its own candidate only when the frozen
selection policy passes confirmation. Its candidate, model identity and record
are displayed separately; it does not replace the all-race recommendation.
Never retune either threshold or model after audit to force promotion.

`model-v6.json` records every candidate/fold, chosen models, calibration mappings,
fixed rules, counts, coverage, confidence intervals and deployment decisions.
`evaluation-v6.json` contains race-level outcomes and predictions. Actual user
records remain separate from retrospective evaluation, retain the first saved
prediction and distinguish all vs selected candidates. Badges expire after the
start time or when the source is older than 30 minutes.

## Checks and operations

Run `python tests/test_v6.py`, `node tests/ui.cjs` and (after fitting and live
feature attachment) `node tests/model-v6.cjs`. These cover temporal exclusion,
field-order invariance, training/live feature parity, serialized estimator parity,
model/feature fallback, actual one-click selectors, manual/stale/past record guards
and storage deduplication. No browser-only preview is required for this edit.

The collection workflow persists the expanded dataset on `main`. Its successful
completion triggers the evaluation workflow. Evaluation outputs are preserved on
`main` for review; they do not automatically change the website. The website uses
GitHub Pages on `kra-mobile-pages`. Its existing data updater additionally refreshes
the completed-date history context and attaches versioned features. No odds feed,
external inference service or new account is needed.

The browser reads latest.json from the public raw data branch (CORS enabled),
with a same-origin fallback. This avoids relying on a Pages rebuild after a
GITHUB_TOKEN data commit. Source timestamps still govern freshness; a cached
or failed fallback can never earn a fresh selective badge. Model/code releases
continue through the ordinary Pages deployment.
